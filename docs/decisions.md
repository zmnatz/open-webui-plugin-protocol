# Decisions and assumptions for 0.1.0

The first standalone release was cut without a round of review, so these are the calls made, recorded so each can be revisited.

## Packaging

- **A Python package on PyPI, run with `uvx owpp`.** The people who write plugins write Python, `owpp check` already needed `python3`, and the runtime and libraries are Python, so one language and one toolchain (uv, pytest, ruff) covers the CLI, the libraries and their tests. The CLI began as a Bun script and was ported before the first release. Its one dependency is PyYAML (the manifest and `SKILL.md` front matter are YAML). Python 3.10 or newer. Releases are published from a `v*` tag with PyPI trusted publishing (`.github/workflows/publish.yml`).
- **No npm package.** Two implementations would need permanent parity work; a Node wrapper around `uvx` would add a runtime without adding anything.
- **The libraries ship inside the package** (`src/owpp/runtime/`), so a bundle depends only on the installed version of `owpp` and the folder.
- **YAML 1.2 scalars.** `plugin.yaml` is read so that only `true`/`false` are booleans and `on`, `no` and `12:30` stay text; a header value is deployed as written, not reinterpreted.
- **One CLI, `owpp`,** with `list`, `check`, `bundle`, `deploy`, `init`. The old per-repo command (`plugin <id> <action>`) became `owpp <action> <id>` so `check` and `deploy` can take several ids.
- **A composite GitHub Action at the repository root** (`action.yml`), rather than a reusable workflow, so consumers keep their own triggers. It builds `owpp` from its own checkout (`uvx --from "$GITHUB_ACTION_PATH"`), so the pinned `uses:` ref decides the version and it does not need PyPI.
- **Version 0.1.0.** The protocol works and is tested, but has not been run against a live Open-WebUI as a package, and manifests carry no protocol version yet. 1.0 should come after a live run and a `protocol:` key in `plugin.yaml`.

## Defaults

- **Plugins folder** `./plugins`, overridable by `--dir` or `OWPP_PLUGINS_DIR` (the old `FUNCTIONS_DIR` is still read).
- **Ownership marker** `open-webui-plugin-protocol`, overridable by `--managed-by` or `OWPP_MANAGED_BY`. Existing deployments must pass their old marker ([adopting](adopting.md#keep-your-existing-marker)).
- **No default URL.** `OPEN_WEBUI_URL` is required; a default would point someone's deploy at someone else's server.
- **Description note** is generic ("Git-controlled: edits made here are overwritten on the next deploy."), with no repository path in it.

## Examples

- Five plugins ship as examples, chosen to cover the protocol: `excalidraw` (filter + tool + `shared.py` + `chat_data` + `routes` + a `templates/` page; self-hostable editor), `mcpo_sync` (event, `PluginScheduledSync`, a `config.yaml`), `stale_data` (event, routes, a `templates/index.html` page behind `user: PluginAdmin`), `inline_visualizer` (a tool and skill from a pinned third-party commit, with a generated parent) and `page_banners` (event; `assets/loader.js` and `assets/custom.css` published through the Shared Assets Protocol).
- They were taken from a working deployment and scrubbed of site-specific details (host names, compose paths, internal decision records). `mcpo_sync` dropped a migration path for a predecessor that only existed there, and its default URL is `http://mcpo:8000`.
- `page_banners` is a variant of Classic298's Better Banners (BSD-3-Clause, notice kept in `NOTICE.md`), reorganised: the script and stylesheet are files, the CSS is carried by the protocol's `custom.css` instead of being injected by the script, and the element ids, classes and socket event are renamed so it can be installed beside the original.
- **Excalidraw can run with nothing from the internet, by self-hosting, not by embedding.** Bundling the editor into the function was measured and refused: about 3.3 MB of minified JavaScript up front (6.8 MB if the bundler follows every lazy import), plus the stylesheet and fonts, would take the plugin's code in Open-WebUI's database from about 95 KB to 2 MB or more, loaded on every worker start and shown in the admin code editor, with a token-in-the-URL route and CORS headers needed because the sandboxed iframe sends no cookies. Instead `self-host/build.sh` builds a folder from pinned versions, the operator serves it with a CORS header, and `EXCALIDRAW_ASSETS_URL` (an environment template in `config.yaml`) points the page at it. Empty keeps esm.sh.

## Environment templates

- **Resolved in the container, never by `owpp`.** `${NAME:-default}` in `jobs:` and `config.yaml` is embedded as written and resolved by `plugin_env` when the plugin loads inside Open-WebUI. Expanding it while bundling would make a bundle depend on the machine that built it, break the rule that a bundle depends only on the folder and the pinned commits, and risk copying a CI secret into code that Open-WebUI stores and admins can read. `owpp check` lists the variables instead, so they are discoverable.
- **Typed when a whole value.** `${N:-60}` is a number, `${FLAG:-true}` a boolean, with YAML 1.2 scalar rules; a bad value for the interval falls back to 60 with a warning rather than stopping the plugin from loading.
- **Not in `function.valves`.** Those are applied by `owpp deploy` through the API with the literal value, which is a different moment and machine from the container's environment.

## Routes and access

- **Signed in by default; public only on purpose.** Every route a plugin mounts requires a signed-in user (Open-WebUI's own session, pending accounts excluded), the static files included. This began as "no public routes" and was relaxed deliberately: some endpoints genuinely cannot ask for a login (a webhook, an OAuth callback, a health check, files fetched by an iframe that sends no cookies). So `access="public"` exists, but it takes the exact word (`"Public"`, `True`, `"none"` are errors, so a typo cannot open a mount), it is **per mount** because a mount's guard covers every route in it (a public endpoint gets a mount of its own, a marker inside it can still ask for more), it is still switched off with the function, and `owpp check` prints a `note` for every public mount and public static folder (it does not fail, even with `--strict`; it is for the reviewer).
- **`static/` and `templates/` instead of `public/` and `dynamic:`.** The old folder was misnamed (everything in it needed a login) and did two jobs: files served as they are, and, through a `dynamic:` list, files the function renders itself and never serves. They are now two folders, as in Flask and Django: `static/` (served; `static: {prefix, access}`) and `templates/` (embedded, read with `plugin_template_text()`, never served, nothing to declare). Anything left under the old names is **refused with a message saying where it went**, not ignored, because a folder that silently stops being served, or a `public: {access: admin}` that silently stops restricting, is the failure to avoid.
- **Access is marked, not coded, and not declared plugin-wide.** A route is marked by the type of a parameter of its handler, a mount has an `access` level in code, and the static files have `static: {access: user | admin | public}`. There used to be a plugin-wide `routes: {access: ...}` key; it went stale once every example used markers (its only unique job was the level of the static files, which have no handler to mark), so it was removed, and the manifest now **refuses** it by name instead of ignoring it, because a silently ignored security setting would leave an author believing a plugin was admin-only. Anything unknown at the top of `plugin.yaml` is refused for the same reason. The status codes are 404 (disabled, checked first so a disabled plugin reveals nothing), 401 (no session) and 403 (not an admin).
- **A missing session on a page is not a dead end.** Sign-ins such as trusted headers or no-auth happen on the app's first page load, so a person opening a plugin's address first has no cookie. The guard tries the no-input sign-ins by calling Open-WebUI's own sign-in endpoint **in-process** (an ASGI call on the app, not a network request to a guessed host and port) with the request's headers, passes the cookie on, and otherwise redirects a top-level navigation to `/auth?redirect=...` so OIDC, LDAP and passwords go through the login page. Iframes get 401, API calls get 401 and never have a session minted. **Assumptions about Open-WebUI not yet checked against a live instance:** the `/api/v1/auths/signin` endpoint accepts empty credentials when a trusted header is configured, and the login page honours `?redirect=`.
- **One explicit exception, `guard=`.** An API called from a sandboxed iframe cannot carry a session, so a mount may replace the sign-in check with its own dependency, which must verify a credential minted from a real login. The library supplies that credential (`plugin_token` / `plugin_check_token`: signed, expiring, scoped to the function and to one subject) so no plugin hand-writes crypto, but it cannot check that the minting page was itself guarded, so the exception stays documented and is used once (Excalidraw).
- **A mount's `name` is its identity**, not its prefix, so a mount that moved (a configurable path) replaces its old self and a plugin keeps no state to do it. Matching is by the tags a mount puts on what it adds: current FastAPI adds one wrapper object per router, with no path or endpoint to match on.
- **No bypass.** `owpp` refuses a `function.py` that adds routes straight to the app. Plugins loaded from a pinned `source:` are not scanned: their code is whatever upstream wrote.
- **The examples were changed to match.** `stale_data` lost its `REQUIRE_ADMIN` valve (its route is marked `user: PluginAdmin` now, with no way to open it up in the UI), and Excalidraw lost its `REQUIRE_LOGIN` valve and with it the permanent per-chat link token that anyone holding a URL could use.
- **A route is marked by the type of a parameter** (`user: PluginAdmin`, `user: PluginUser`): FastAPI's own `Annotated` idiom, so the handler also receives the user. A marker only tightens the mount's level, never loosens it, and there is no public marker (public is a property of a mount, not of a route). A route with no marker is open to any signed-in user, which is the documented default.
- **Events are handled by decorator** (`@on("event.name", own=True)` on a method of `class Event(PluginEvents)`), not by an `event()` of `if` checks. The list of known event names is not closed (Open-WebUI adds events), so `owpp check` refuses only a malformed name or one that looks like a typo of a known one, and a class with `@on` handlers that does not inherit `PluginEvents`. The jobs and assets libraries' mixins are built on it too (`plugin_sync_event` is gone), so one dispatcher and one `own` rule serve every handler. The plugin runtime's event sink (`_PluginSink`) stays as it is: it exists because a disabled function never loads, so a method on the function's own class could not hear its disable or delete.
- **A chat is marked by the type of its path parameter** (`chat_id: WritableChat` / `ReadableChat`), checked with Open-WebUI's own `Chats.has_chat_access`. No access is a 404, so a chat's existence is not revealed. A temporary chat (`local:...`) has no record to check and passes for any signed-in user, which is a stated limit, not a guarantee. Other kinds of per-resource check (a note, a file, a knowledge base) are not covered; they stay in the function, using the user it is given.

## Assets and the Shared Assets Protocol

- **`assets/` is the protocol's two files, nothing more.** `assets/loader.js` and `assets/custom.css` are a plugin's fragments of `/static/loader.js` and `/static/custom.css`; any other file there is an error. A page or template the function renders stays in `public/` with `dynamic`.
- **The protocol blocks stay byte-identical.** Everything `owpp` adds (the registration, the `try/catch` wrap, `asset_vars()` placeholders, the disable/delete handling) is its own library beside them, never edits to them; the newest `ASSET_IMPL_VERSION` still wins across plugins.
- **`loader.js` is written as a body and wrapped by `owpp`** (own function scope, strict mode, `try/catch`, as the protocol asks), so authors do not hand-write an IIFE. The wrapper cannot catch a syntax error and makes top-level declarations local; both are documented. It is readable, not minified or obfuscated. `wrap: false` opts out.
- **`live_reload` is opt-in** (`include: [live_reload]`): it needs Open-WebUI 0.11+ and imports `JSONCodec` at load, so it would break older instances if it were automatic.
- **Not verified against a live Open-WebUI.** The assets library is tested through the real protocol block and Starlette routing (`tests/test_assets.py`), with Open-WebUI's own modules stubbed.

## Documentation and review

- **A documentation site, built with Zensical, published to GitHub Pages.** The first version used MkDocs with the Material theme, and was dropped before it merged. Material for MkDocs reaches end of life on 2027-05-05. MkDocs itself had its last 1.x release in 2024, and its 2.0, already in pre-release, removes the plugin system and support for existing themes. So the plain MkDocs theme would only have moved the problem. Zensical is the Material team's successor: Python, so it installs with uv like everything else (`uv sync --group docs`), and it builds the existing `docs/*.md` as they are. It is new (0.1.2) and needs Python 3.11 or newer, so the `docs` group carries a marker and the library itself still supports 3.10. That is acceptable for a prototype. Docusaurus was the other candidate: stable, but it brings a Node toolchain into a Python repository for features nothing here needs.
- **The pages for review are generated, never written by hand.** The test catalogue comes from the test docstrings, the audit trail from `git log`, the examples overview from each `plugin.yaml`, and the changelog, security and notice pages from the root files. Generated pages cannot drift from the code, and a test with no description shows up as a gap.
- **The generating is a plain script, not a plugin of the site generator.** `tools/build_docs.py` writes ordinary Markdown into `build/docs/` and then runs Zensical, which knows nothing about it. Link checking (files and headings) happens in the script too. Changing site generators again would mean a new config file, nothing more.
- **Every plugin test says how to repeat it by hand** (`By hand:` in its docstring, [testing](testing.md#describe-every-test)), and `tests/test_test_docs.py` fails when one does not. The mock is not Open-WebUI, so a person still has to see each behaviour on a live instance before a release. The docstring keeps those steps next to the test that covers the same behaviour.
- **The audit trail shows names, never email addresses.** They are stripped from commit trailers before the page is built.
